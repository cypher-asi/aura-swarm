# Staged TEE Rollout

Numbered scripts implementing the Swarm TEE upgrade rollout (R1 dual-mode → R2 migration → R3 cleanup) as discrete, individually verifiable steps. Run them **in order, one at a time**: every script ends with explicit verification of its own step and prints `STEP NN OK — proceed to NN+1` or `STEP NN FAILED: <why>`. All steps are idempotent — re-running after a partial failure is safe.

The pre-TEE-rollout scripts live in [legacy/](legacy/) for reference.

## Prerequisites

- `config.env` (sourced by every script) defines region, cluster, node groups, namespaces, and deploy-operator IAM names.
- `.secrets/` at the repo root: `INTERNAL_TOKEN` and `kbs-admin.key` are generated by step 04 if missing. No LLM provider key is needed — agents reason via the JWT-authenticated `aura-router` proxy (`AURA_ROUTER_URL`), so the deploy injects no Anthropic/OpenAI key. Steps 07/08 additionally need an owner JWT in `SMOKE_TEST_TOKEN` (env or `.secrets/SMOKE_TEST_TOKEN`) for test-agent verification.
- The `aura-harness` image is built and pinned automatically by **step 06** (`06-build-harness.sh`, which clones `cypher-asi/aura-harness` at `HARNESS_REF`). To build a local checkout set `HARNESS_REPO_PATH`, or set `AURA_HARNESS_IMAGE` to a prebuilt `@sha256` digest to skip the build.

### Release refs

Steps that deploy swarm builds accept a git ref via `--ref` or env (defaults shown):

| Stage | Env var | Default |
|---|---|---|
| R1 dual-mode | `SWARM_R1_REF` | `fa93895` |
| R2 migration | `SWARM_R2_REF` | `af9e034` |
| R3 cleanup | `SWARM_R3_REF` | `master` |

Platform images are built from a throwaway git worktree at that ref and tagged with the short commit sha (rebuilds are skipped when the tag already exists in ECR).

## Rollout sequence

| Step | Script | What it does | How you know it worked | Rollback note |
|---|---|---|---|---|
| 00 | `00-preflight.sh` | Read-only: tools, AWS/kubectl auth, cluster reachability, fleet report (pods by runtime class, schema version), zbilling reachability. No mutations. | Every check green; `STEP 00 OK`. | Nothing to roll back. |
| 01 | `01-iam.sh` | Deploy-operator IAM for the SSO org: customer-managed deploy policy attached to the Identity Center **permission set** (`DEPLOY_SSO_PERMISSION_SET`) and re-provisioned. **No cluster service roles** (those stay in terraform). Run with an Identity Center admin session. | Policy exists; permission set references it; deploy role passes `eks:DescribeUpdate` simulation. | Detach the customer-managed policy reference from the permission set and re-provision. |
| 02 | `02-snp-node-group.sh` | Terraform plan/apply for the worker node group + Peer Pods/CAA infra (IRSA role + worker↔pod-VM SG rules). **Aborts before apply** if the plan would REPLACE the EFS filesystem (unencrypted → mandatory encrypted). | Workers Ready; CAA IRSA role applied (`caa_role_arn` output set). | `terraform destroy -target` the affected resources and re-run. |
| 03 | `03-coco-operator.sh` | Cloud API Adaptor (CAA) Helm install (pinned `CAA_CHART_VERSION`): installs the `kata-remote` RuntimeClass and boots a per-agent AWS-managed SEV-SNP pod VM off-cluster. | CAA daemonset Ready on the workers; `kata-remote` RuntimeClass exists. | `helm uninstall cloud-api-adaptor -n confidential-containers-system`. |
| 04 | `04-trustee-kbs.sh` | Trustee KBS (built-in AS) deploy, KBS admin keypair (`.secrets/kbs-admin.key` ↔ `kbs-auth-public-key` secret), generates `.secrets/INTERNAL_TOKEN` if missing. | KBS pod ready; service resolves + HTTP listener answers in-cluster. | Delete the kbs deployment; per-agent DEKs live on the persistent `kbs-repository` PVC. |
| 05 | `05-peer-pods-smoke-test.sh` | Throwaway pod on `kata-remote` boots a per-agent SEV-SNP pod VM, attests, fetches a scratch DEK via the in-guest CDH; asserts the pod VM is created **and** terminated. Scratch resource provisioned via `kbs-client` and deleted afterwards. | Pod succeeds, fetched value matches, pod VM terminated — end-to-end attestation proven before any product traffic. | Fully self-cleaning (pod, pod VM, setter, secret, scratch resource). |
| 06 | `06-build-harness.sh` | Build + pin the `aura-harness` image: clones `cypher-asi/aura-harness` at `HARNESS_REF` (or builds `HARNESS_REPO_PATH`), `docker build`+push to ECR, resolves the immutable `@sha256` digest, writes `.last-harness-image.env`. Set `AURA_HARNESS_IMAGE` to skip the build. | Image pushed; pinned digest persisted; `STEP 06 OK`. | Re-run with a different `HARNESS_REF`; or set `AURA_HARNESS_IMAGE` to a known-good digest. |
| 07 | `07-deploy-r1.sh` | Build+push+deploy gateway/control/scheduler at the **R1 ref** (dual-mode); pins agent pods to the step-06 harness digest. | Rollouts complete; `/internal/health` ok; legacy kata-fc pods byte-for-byte untouched (pod set, runtime class, spec hash); one test agent lands on `kata-remote` with sealed env and a billing sku, then is destroyed. | Redeploy previous images (`--ref` an older sha). Legacy agents were never touched. |
| 08 | `08-r1-soak-check.sh` | Repeatable soak verification: platform health, fleet read-only checks, vault round-trip, tier change, cron wake→run→hibernate, usage + logs APIs — mutations only on its own test agent. | Printed checklist all PASS. | Read-only against prod agents; nothing to roll back. |
| 09 | `09-efs-backup.sh` | On-demand AWS Backup recovery point of the swarm EFS — **the R2 rollback point** — persisted in `.last-efs-backup.env`. | Backup job `COMPLETED`; recovery point ARN recorded. | This step *is* the rollback provision. |
| 10 | `10-deploy-r2-migrate.sh` | Refuses without the step-09 backup. Deploys the **R2 ref**; gateway runs the v1→v2 store migration + DEK backfill at startup; then sets `MIGRATION_RECREATE_LEGACY_PODS=true` and monitors the rolling recreation with pods-remaining progress. | `schema_version=2` via `/internal/health`; migration/backfill log lines; zero running kata-fc pods. | Restore the step-09 recovery point, redeploy R1 (`07`), unset the ConfigMap gate. |
| 11 | `11-r2-convergence.sh` | Convergence **gate**: schema v2, every record tiered + sealed (billing skus derivable), all pods on `kata-remote`, zero kata-fc, spot-check of N pods' sealed-state env. Refuses to pass otherwise. | `STEP 11 OK`. Safe to re-run while hibernating stragglers wake/migrate. | Same as step 10. |
| 12 | `12-deploy-r3-cleanup.sh` | Gated on 11. Deploys the **R3 ref**, deletes the `kata-fc` RuntimeClass, terraform-applies the shrunk system pool (with the EFS hazard guard re-checked). | No kata-fc artifacts remain; agent pods Running/Ready; fleet report healthy. | Point of low return: R3 code drops legacy paths. Restore = step-09 recovery point + R2 images. |
| 13 | `13-finalize.sh` | Final fleet health report; EFS backup retention reminder — prompts for deletion only after the retention window (`EFS_BACKUP_RETENTION_DAYS`, default 14), never auto-deletes. | All report lines green; `STEP 13 OK`. | n/a |

### Conditional remediations (not part of the linear flow)

| Script | When to run | What it does |
|---|---|---|
| `efs-encryption-migration.sh` | Only if step 02 ABORTS because the live EFS filesystem is unencrypted (the storage module mandates `encrypted=true`). | Guided unencrypted→encrypted EFS migration (new FS, rsync via temp pod, PVC rebind, terraform state repoint) with explicit pause points. Verify final rsync (file counts match) and a replacement-free plan, then re-run step 02. The old filesystem is kept untouched until you delete it manually. |

## R1 soak guidance

Between steps 07 and 09, soak R1 in production for as long as you need confidence: run `./08-r1-soak-check.sh` **repeatedly** during the window (it is cheap and read-only against prod agents). Use `--keep-agent` once and `--agent-id <id>` on subsequent runs to keep a single designated test agent for the whole soak. Only move on to 09/10 when soak runs pass consistently and the R1 exit criteria hold (new agents attest + seal, legacy agents show zero behavior change, tier billing visible in zbilling).

## Shared assets

- `terraform/` — root module + network/storage/eks/ecr modules (EFS encryption is mandatory in the storage module; that is exactly what the step-02 hazard guard protects against on brownfield clusters).
- `iam/` — deploy-operator IAM policy template (applied by step 01 only).
- `k8s/` — platform manifests, templated at deploy time (images, secrets, EFS id) by the deploy steps; never edited in place.
- `config.env` — environment knobs shared by all steps.
- `_lib.sh` — step framing, terraform/ECR/port-forward helpers reused across scripts.
- `legacy/` — pre-TEE-rollout scripts, kept for reference (including `destroy.sh`, `diagnose.sh`, `fix-pending-pods.sh`, and the image build tooling `07-build-images.sh`).
