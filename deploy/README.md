# Staged TEE Rollout

Numbered scripts implementing the Swarm TEE upgrade rollout (R1 dual-mode → R2 migration → R3 cleanup) as discrete, individually verifiable steps. Run them **in order, one at a time**: every script ends with explicit verification of its own step and prints `STEP NN OK — proceed to NN+1` or `STEP NN FAILED: <why>`. All steps are idempotent — re-running after a partial failure is safe.

The pre-TEE-rollout scripts live in [legacy/](legacy/) for reference.

## Prerequisites

- `config.env` (sourced by every script) defines region, cluster, node groups, namespaces, and the `org-admin`/`ops-admin` permission-set + policy names (see [Separation of duties](#separation-of-duties)).
- `.secrets/` at the repo root: `INTERNAL_TOKEN` and `kbs-admin.key` are generated by step 04 if missing. No LLM provider key is needed — agents reason via the JWT-authenticated `aura-router` proxy (`AURA_ROUTER_URL`), so the deploy injects no Anthropic/OpenAI key. Steps 07/08 additionally need an owner JWT in `SMOKE_TEST_TOKEN` (env or `.secrets/SMOKE_TEST_TOKEN`) for test-agent verification.
- The `aura-harness` image is built and pinned automatically by **step 06** (`06-build-harness.sh`, which clones `cypher-asi/aura-harness` at `HARNESS_REF`). To build a local checkout set `HARNESS_REPO_PATH`, or set `AURA_HARNESS_IMAGE` to a prebuilt `@sha256` digest to skip the build.

### Release refs

Steps that deploy swarm builds accept a git ref via `--ref` or env (defaults shown):

| Stage | Env var | Default |
|---|---|---|
| R1 dual-mode | `SWARM_R1_REF` | `fa93895` |
| R2 migration | `SWARM_R2_REF` | `af9e034` |
| R3 cleanup | `SWARM_R3_REF` | `master` |

Platform images are built from a throwaway git worktree at that ref and tagged with the short commit sha (rebuilds are skipped when the tag already exists in ECR).

## Rollout sequence

Each stage is runnable by exactly **one** Identity Center user and is labeled in the Owner column (and in the `STEP NN OK [owner]` line). `org-admin` owns ALL IAM and runs **only** step 01; every other stage is `ops-admin`. See [Separation of duties](#separation-of-duties) below for the `01 → 02 → 01 (re-run) → 03` ordering.

| Step | Owner | Script | What it does | How you know it worked | Rollback note |
|---|---|---|---|---|---|
| 00 | ops-admin | `00-preflight.sh` | Read-only: tools, AWS/kubectl auth, cluster reachability, fleet report (pods by runtime class, schema version), zbilling reachability. No mutations. | Every check green; `STEP 00 OK [ops-admin]`. | Nothing to roll back. |
| 01 | org-admin | `01-iam.sh` | **All deploy IAM, consolidated under org-admin.** Provisions two customer-managed policies attached to the `org-admin` / `ops-admin` Identity Center **permission sets**; the EKS cluster + node service roles terraform reads/passes; and (cluster-aware) the IRSA OIDC provider + Peer Pods/CAA IRSA role (incl. `ec2:Describe*`). Run with an Identity Center admin session. **Run twice**: before step 02 (roles), then again after step 02 (OIDC + CAA role). | Both policies + permission sets wired; cluster/node roles exist; on the post-cluster pass the CAA role + OIDC provider exist; `ops-admin` passes the `eks:DescribeUpdate` simulation. | Detach the policy references from the permission sets and re-provision; delete the created roles/OIDC provider. |
| 02 | ops-admin | `02-snp-node-group.sh` | Auto-discovers + pins the pod-VM AMI (`PODVM_AMI_ID`), then terraform plan/apply for the worker node group + Peer Pods/CAA infra (worker↔pod-VM SG rules). Reads the org-admin cluster/node roles via data sources. **Aborts before apply** if the plan would REPLACE the EFS filesystem (unencrypted → mandatory encrypted). | Workers Ready; cluster/node SGs applied; `PODVM_AMI_ID` persisted. | `terraform destroy -target` the affected resources and re-run. To pin a specific image: `./configure.sh PODVM_AMI_ID=ami-XXXX` before step 02. |
| 03 | ops-admin | `03-coco-operator.sh` | Cloud API Adaptor (CAA) Helm install (pinned `CAA_CHART_VERSION`): installs the `kata-remote` RuntimeClass and boots a per-agent AWS-managed SEV-SNP pod VM off-cluster. Wires the CAA SA to the org-admin IRSA role (ARN derived from account+prefix; `iam:GetRole`-validated). | CAA daemonset Ready on the workers; `kata-remote` RuntimeClass exists. | `helm uninstall cloud-api-adaptor -n confidential-containers-system`. |
| 04 | ops-admin | `04-trustee-kbs.sh` | Trustee KBS (built-in AS) deploy, KBS admin keypair (`.secrets/kbs-admin.key` ↔ `kbs-auth-public-key` secret), generates `.secrets/INTERNAL_TOKEN` if missing. | KBS pod ready; service resolves + HTTP listener answers in-cluster. | Delete the kbs deployment; per-agent DEKs live on the persistent `kbs-repository` PVC. |
| 05 | ops-admin | `05-peer-pods-smoke-test.sh` | Throwaway pod on `kata-remote` boots a per-agent SEV-SNP pod VM, attests, fetches a scratch DEK via the in-guest CDH; asserts the pod VM is created **and** terminated. Scratch resource provisioned via `kbs-client` and deleted afterwards. | Pod succeeds, fetched value matches, pod VM terminated — end-to-end attestation proven before any product traffic. | Fully self-cleaning (pod, pod VM, setter, secret, scratch resource). |
| 06 | ops-admin | `06-build-harness.sh` | Build + pin the `aura-harness` image: clones `cypher-asi/aura-harness` at `HARNESS_REF` (or builds `HARNESS_REPO_PATH`), `docker build`+push to ECR, resolves the immutable `@sha256` digest, writes `.last-harness-image.env`. Set `AURA_HARNESS_IMAGE` to skip the build. | Image pushed; pinned digest persisted; `STEP 06 OK`. | Re-run with a different `HARNESS_REF`; or set `AURA_HARNESS_IMAGE` to a known-good digest. |
| 07 | ops-admin | `07-deploy-r1.sh` | Build+push+deploy gateway/control/scheduler at the **R1 ref** (dual-mode); pins agent pods to the step-06 harness digest. | Rollouts complete; `/internal/health` ok; legacy kata-fc pods byte-for-byte untouched (pod set, runtime class, spec hash); one test agent lands on `kata-remote` with sealed env and a billing sku, then is destroyed. | Redeploy previous images (`--ref` an older sha). Legacy agents were never touched. |
| 08 | ops-admin | `08-r1-soak-check.sh` | Repeatable soak verification: platform health, fleet read-only checks, vault round-trip, tier change, cron wake→run→hibernate, usage + logs APIs — mutations only on its own test agent. | Printed checklist all PASS. | Read-only against prod agents; nothing to roll back. |
| 09 | ops-admin | `09-efs-backup.sh` | On-demand AWS Backup recovery point of the swarm EFS — **the R2 rollback point** — persisted in `.last-efs-backup.env`. | Backup job `COMPLETED`; recovery point ARN recorded. | This step *is* the rollback provision. |

### Separation of duties

IAM is consolidated under **org-admin** (the only stage org-admin runs); **ops-admin** runs everything else with no IAM-write permission (only a scoped `iam:PassRole` + `iam:Get*/List*` on the cluster/node role ARNs). Because the CAA IRSA trust references the cluster OIDC issuer — which only exists after terraform creates the cluster — step 01 is **cluster-aware** and runs twice:

```
01 (org-admin)  → policies + permission sets + cluster/node roles   [CAA/OIDC deferred]
02 (ops-admin)  → terraform: cluster, node group, SGs, addons, ECR
01 (org-admin)  → now the cluster exists → OIDC provider + CAA IRSA role (incl. ec2:Describe*)
03 (ops-admin)  → CAA Helm install (wires the SA to the CAA role) → ...
```

The two policy templates live in [iam/org-admin-policy.json](iam/org-admin-policy.json) and [iam/ops-admin-policy.json](iam/ops-admin-policy.json); permission-set + policy names are in [config.env](config.env) (`ORG_*` / `OPS_*`).

### Conditional remediations (not part of the linear flow)

| Owner | Script | When to run | What it does |
|---|---|---|---|
| ops-admin | `efs-encryption-migration.sh` | Only if step 02 ABORTS because the live EFS filesystem is unencrypted (the storage module mandates `encrypted=true`). | Guided unencrypted→encrypted EFS migration (new FS, rsync via temp pod, PVC rebind, terraform state repoint) with explicit pause points. Verify final rsync (file counts match) and a replacement-free plan, then re-run step 02. The old filesystem is kept untouched until you delete it manually. |

## R1 soak guidance

Between steps 07 and 09, soak R1 in production for as long as you need confidence: run `./08-r1-soak-check.sh` **repeatedly** during the window (it is cheap and read-only against prod agents). Use `--keep-agent` once and `--agent-id <id>` on subsequent runs to keep a single designated test agent for the whole soak. Only move on to 09/10 when soak runs pass consistently and the R1 exit criteria hold (new agents attest + seal, legacy agents show zero behavior change, tier billing visible in zbilling).

## Shared assets

- `terraform/` — root module + network/storage/eks/ecr modules (EFS encryption is mandatory in the storage module; that is exactly what the step-02 hazard guard protects against on brownfield clusters).
- `iam/` — the `org-admin`/`ops-admin` IAM policy templates (applied by step 01 only).
- `k8s/` — platform manifests, templated at deploy time (images, secrets, EFS id) by the deploy steps; never edited in place.
- `config.env` — environment knobs shared by all steps.
- `_lib.sh` — step framing, terraform/ECR/port-forward helpers reused across scripts.
- `legacy/` — pre-TEE-rollout scripts, kept for reference (including `destroy.sh`, `diagnose.sh`, `fix-pending-pods.sh`, and the image build tooling `07-build-images.sh`).
